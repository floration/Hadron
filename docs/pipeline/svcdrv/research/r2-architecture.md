## 3. Where the TrustedInstaller code lives: recommend `core/sys/token.{h,cpp}` (core API change, lead)

| Option | Verdict |
|---|---|
| Copy from runas | No. Two copies of privileged token code to review and fix. They have already drifted: the runas copy never restores TI's state. |
| Shared header in `modules/runas` | No. `mod_services` would include or link runas internals, so `HadronServices.exe` would depend on another module's library. That breaks module independence and still leaves the code in an anonymous namespace. |
| **Move to `core/sys/token.h`** | **Yes.** One reviewed implementation, and runas is refactored onto it in the same PR, so runas's selftest proves the move kept behaviour. The lead makes it (CLAUDE.md: core API changes are never handed off). |

Proposed surface (lead to finalise):
```cpp
namespace hx::sys {
class ThreadPrivilege;   // moved as-is: ImpersonateSelf + enable on the thread token, RevertToSelf in dtor
class ThreadTokenSwap;   // moved as-is: save/restore the thread token
// SYSTEM impersonation token from winlogon in our session (needs SeDebugPrivilege on the thread).
HANDLE OpenSystemToken(TOKEN_TYPE type, DWORD* err);
// TrustedInstaller token: starts the service if stopped (*started = true), opens and duplicates its token while
// impersonating SYSTEM. type = TokenImpersonation for in-process writes, TokenPrimary for runas launches.
// The session move (SeTcb) stays in runas: only process launches need it.
HANDLE OpenTrustedInstallerToken(TOKEN_TYPE type, bool* started, DWORD* err);
// Stop TI again only if we started it (the idea's "left in the state it was found").
bool RestoreTrustedInstaller(bool started, DWORD* err);
// Reads the thread token's user back ("NT SERVICE\TrustedInstaller"), so the UI can be honest.
std::wstring ThreadTokenUser();
}
```

How services uses it:
- The apply Worker takes the TI token **once per apply**, only when the plan contains a TI-marked item.
- It wraps **each** TI-marked SCM call in `ThreadTokenSwap`. SCM RPC uses the thread's impersonation token.
  The UI thread is never impersonated.
- It checks `ThreadTokenUser()` before the write and logs the identity in the undo log `I` line.
- After the batch it restores TI's state.

Without SeTcb or a session move, the services path is *simpler* than runas's.

Open for the Windows researcher:
- Whether SCM still refuses `ChangeServiceConfigW` on a launch-protected service (WinDefend with Tamper
  Protection) even under TI.
- If it does, whether a TI `HKLM\...\Services\<n>\Start` registry write is the fallback.

Don't build the registry fallback in v1 unless research shows the owner's target items need it.

## 4. The stock-service KB: storage, generator and rule 7

**Storage:**
- `tools/services/kb.py` is the source; `genkb.py` is the gate.
- Output: `modules/services/data/services.db`, UTF-8 TSV, escaped exactly like bios settings.db (`\\`, `\n`,
  TAB becomes a space).
- Committed and embedded as RCDATA `SERVICES_KB` through an INTERFACE `.rc` (bios pattern). Same generator
  output as CI `cmp`.

**Every entry is tier 1.** There's no tier 2. Fewer rules, and every entry carries a basis.

Record (one `E(...)` in kb.py, one `K` line in the db):

| Field | Meaning |
|---|---|
| `name` | service key name (case-insensitive match) |
| `kind` | `svc` or `drv` |
| `builds` | e.g. `19045` (Win10 22H2). An item matches only when the running build is listed; otherwise "no explanation, not in any preset" (idea risk "Build differences"). |
| `title`, `expl` | what it does |
| `if_off` | what stops working when it's disabled |
| `test` | "test it, and how" when the effect depends on workload |
| `levels` | preset membership and target, e.g. `bloat=4` (later `stripped=3 minimum=4`) |
| `why` | one line per level: the reason shown in the plan |
| `sysok` | a System-start driver may appear in a preset (the curated list); default false |
| `never` | never in any preset, a hard guard (RpcSs, DcomLaunch, the Boot-start set, ...) |
| `basis`, `basis_note`, `sources` | for the explanation, same semantics as bios |
| `pbasis`, `pbasis_note` | for the **preset membership** claim ("this is bloat" is a claim, per the idea's honesty risk) |

**Generator checks** (reuse, don't rewrite):
- `tools/services/genkb.py` imports `render`, `render_basis`, `unmarked_numbers` and the denylist from
  `tools/bios/genkb.py` by adding `tools/bios` to `sys.path`. Zero change to the bios generator, whose output CI
  pins byte-for-byte.
- Factor out a shared `tools/kbcheck.py` later.

It fails when:
- an entry has no `basis`;
- an entry has a non-empty `levels` and no `pbasis`;
- a basis is unknown;
- an owner-measured basis has no `@OWNER*` key, or a published basis has no https key;
- any number in title/expl/if_off/test/why/basis_note is outside a `[[text|kind|ref]]` marker;
- there's owner-specific text;
- `levels` targets a start type other than 3/4;
- a `never` entry has levels;
- a `drv` entry is in a level without `sysok`.

The Boot/System check is repeated at runtime against the *live* start type, because the KB can't know it (§7).

**UI** shows the basis and basis note in the detail pane, and the plan shows each row's `pbasis`. `folklore` is
shown as "folklore (repeated, no evidence)". There's no RAM or "MB saved" text anywhere: such numbers would need
an owner-measured or published basis, and the measured before/after is deferred (§8).

**Free win:** show Windows' own registered description (`QueryServiceConfig2W(SERVICE_CONFIG_DESCRIPTION)`) for
**every** item, labelled "Description (from the service's registration)".
- It isn't Hadron's claim, so it needs no basis.
- It answers "explains what they do" for all items, third-party included, on day one, with no KB work.
- Hadron's KB text then only adds what Windows doesn't say: what breaks, why it's in a preset, and how to test.
- Note for the lead: the idea says third-party items show "path, company, signer only". Showing their registered
  description as well is additive, so log it as a proxy or lead decision.

## 5. File formats, locations and flush ordering

**Locations:**
- Everything goes in `%LOCALAPPDATA%\Hadron\services\`, via `SHGetKnownFolderPath(FOLDERID_LocalAppData)`, even
  in portable mode. Recovery data must sit on the Windows volume (see restore.cmd below).
- The directory is created if missing. In selftest and screenshot mode the root is injected (a temp dir or the
  fixture dir) and %LOCALAPPDATA% is never touched.

```
services\first.txt                    first-run snapshot; CREATE_NEW, never rewritten
services\snap-<stamp>.txt             full snapshot taken before each apply
services\undo-<stamp>.log             one per apply (an undo is itself an apply, with its own log)
services\recovery\<stamp>\restore.cmd + README.txt   restores that apply's "before" values offline
services\recovery\first\restore.cmd + README.txt     restores first.txt's start types (written once, at first run)
services\recovery-<stamp>.zip, recovery-first.zip    the same folders zipped (rule 6), stored method, UTF-8 flag
```
`<stamp>` = `yyyyMMdd-HHmmss` local time, with a `-N` suffix on collision. Every file is created with
`CREATE_NEW`, so nothing is ever overwritten.

**Common text rules:**
- UTF-8, no BOM, LF, TAB-separated, bios escaping.
- Line 1 is a magic header: `HXSVC\t1\t<snapshot|undo>`.
- Unknown line kinds are skipped, for forward compatibility.
- Size caps like bios (16 MB per file).
- Own parser, rule 3.

**Snapshot** (also the fixture format, so one parser serves first-run, pre-apply, drift and fixtures):
```
M  key  value                       created, build (10.0.19045.x), hadron version, kind first|pre-apply
S  name  display  type(hex)  start(0-4)  delayed(0/1)  trigger(0/1)  state(1-7)  errctl  account  image
   group  deps(';'-joined)  description
X  name  key=value ...              fixture only: acl=ti (admin write -> ACCESS_DENIED), company=, fail=...
```

**Undo log** (append-only):
```
HXSVC 1 undo
B  stamp  source(preset id | single | undo:<stamp>)  count
P  seq  name  field(start|state)  before  after  identity(admin|ti)   all plan rows, written + flushed up front
I  seq  observed-before             about to change; re-read live value; flushed BEFORE the SCM call
D  seq  ok|skip|fail  after-observed  error-text      flushed after the call and a re-read
E  stamp                            apply finished
```

**Apply order**, on the Worker, after the user confirms the in-view plan:
1. Take the lock: named mutex `Local\Hadron.services.apply` (suite and standalone can't both apply), plus the log
   opened with share mode 0.
2. Write `snap-<stamp>.txt`, then `FlushFileBuffers`, then close.
3. Write `recovery\<stamp>\restore.cmd` and README.txt (flushed), then `recovery-<stamp>.zip` (flushed).
   **If any of steps 1-3 fails, abort with the error and change nothing.**
4. Create `undo-<stamp>.log`, write the header, `B` and every `P` line, and flush.
5. For each row:
   - re-read the live config;
   - if it no longer equals the plan's "before", write a `D skip drifted` line and continue;
   - otherwise write `I` and flush, then call SCM (as TI if marked), re-read, write `D` and flush.
6. Write `E` and flush. Then restore TI's state and post done.

**Startup:** scan `undo-*.log`. A log with `B` but no `E` brings up a banner: "An apply was interrupted
(<stamp>): Undo / Resume".
- **Undo** builds a plan of `before` values for rows with `D ok`, plus rows with `I` but no `D` (state unknown,
  so re-read and set).
- **Resume** builds a plan from the `P` rows that have no `D`.

Both are plans: shown, confirmed and logged like any other. The same semantics as `core/fs` in hard rule 1. It
isn't `core/fs` because no files move.

**Undo last apply** (menu): the same as the interrupted-apply Undo, for the newest log that has an `E`.

**restore.cmd:** generated text, golden-tested. Content is for the Windows researcher to check.
- WinRE runs as SYSTEM, so there's no admin check and no `net session` (incident 3).
- Target drive = `%~d0` (the script sits on the Windows volume) or `%1` when copied to a USB stick.
- It refuses if `<drive>\Windows\System32\config\SYSTEM` is missing. That matters because the owner has a second
  Windows install on H: (incident 2), so the script never guesses with a drive-letter loop.
- Steps:
  1. `reg load HKLM\HXOFF <hive>`;
  2. read `HXOFF\Select\Current`;
  3. for each row: `reg query ...\Services\<n> >nul && reg add ...\Services\<n> /v Start /t REG_DWORD /d <v> /f`
     (plus `DelayedAutostart`), never creating keys;
  4. `reg unload`.
- Only start types are restored (state can't be restored offline).

**Rule-6 question for the lead or proxy:**
- WinRE's cmd has no unzip, so a script that exists *only* inside a .zip can't run there.
- Proposal: write the plain `recovery\<stamp>\` folder (runnable in WinRE) **and** the .zip of it (for copying to
  USB or carrying around).
- Rule 6 exists because the owner can't *download* .bat files. A file Hadron writes locally isn't downloaded, so
  the plain copy doesn't break the rule's intent.
- Log this as a decision. If the lead reads rule 6 literally, the fallback is README.txt with the exact commands
  to type.

## 6. Fake service provider, `--screenshot` and `--selftest` under Wine

```cpp
namespace hx::services {
enum class Identity { Admin, TrustedInstaller };
struct Backend {                                   // NOT named IServiceProvider (COM clash)
    virtual ~Backend() = default;
    virtual bool Enumerate(std::vector<SvcItem>* out, std::wstring* err) = 0;        // services + drivers, full config
    virtual bool Dependents(const std::wstring& name, std::vector<std::wstring>* out, std::wstring* err) = 0;
    virtual bool Query(const std::wstring& name, SvcItem* out, std::wstring* err) = 0; // re-read before/after a write
    virtual bool CanWrite(const std::wstring& name, Identity id, DWORD* err) = 0;   // OpenServiceW(SERVICE_CHANGE_CONFIG),
                                                                                    // no change: marks "needs TI" in the plan
    virtual bool SetStart(const std::wstring& name, const StartCfg& c, Identity id, std::wstring* err) = 0;
    virtual bool Control(const std::wstring& name, Op op /*Start|Stop*/, Identity id, std::wstring* err) = 0;
};
std::unique_ptr<Backend> MakeLiveBackend();
std::unique_ptr<Backend> MakeFakeBackend(const std::wstring& snapshotPath);  // + SetFailAt(seq) for crash tests
}
```
- `CanWrite` is how the plan shows "needs TrustedInstaller" **before** anything is written: an access check by
  opening the handle, with nothing changed.
- `LiveBackend`'s write methods do nothing unless `Arm()` was called, and only the UI's confirmed-plan path calls
  it. `LoadFixture()` installs a FakeBackend and a fixture store root, so a fixture run can't reach SCM writes.

**`--screenshot`:**
```
HadronServices.exe --fixture tests/fixtures/services --screenshot s.png
    [--tab drivers] [--select WinDefend] [--plan bloat]
```
- `LoadFixture` loads synchronously with no Worker, and selects the tab, row or plan screen. `--plan` renders the
  plan screen, the screen that matters most for review.
- `tests/fixtures/services/interrupted` renders the banner.
- CI shots: Baseline/Console × dark/light for both tabs, plus a plan shot, plus a suite non-solo shot (mirror bios).

**`--selftest`** works under Wine and MSVC, and is fixture-driven. It never touches real services or
%LOCALAPPDATA%: the store root is a fresh `GetTempPath` dir.
1. Pure: start/state/type text, image-path normalisation, snapshot and undo-log round trip (escapes, unknown
   lines, caps, a truncated last line).
2. KB: the embedded db parses, every entry has a basis, and every entry with levels has a pbasis.
3. Guards (§7), with fixture items built to hit each guard.
4. Engine: plan(bloat) → apply on FakeBackend → state matches → Undo → state equals the original byte-for-byte
   in snapshot form.
5. Crash: `SetFailAt(3)`, then the log has no `E`, then startup detection finds it, then Resume completes. Run
   again: crash, then Undo restores.
6. TI marking: `acl=ti` items are excluded with the switch off and included as `ti` with it on.
7. restore.cmd text equals `tests/golden/services/restore.cmd`. The zip's local and central headers are
   parsed back and its CRC recomputed.
8. Live read-only smoke (`--selftest` with no fixture): `LiveBackend::Enumerate` returns more than 0 items under
   Wine. Writes are never called.

**Real SCM writes** without touching the owner's services:
- `HadronServices.exe --live-test <svc>`, intercepted in standalone.cpp like runas `--launch-test`.
- On the windows-latest job, a CI step creates a throwaway `HadronTestSvc` with `sc.exe create` (the CI script,
  not Hadron source). The live test then sets its start type, verifies it, undoes it and verifies again. The
  script then deletes the service with `sc.exe delete`.
- A TI variant is informational (`continue-on-error`), as runas's is.
- Analyze and Finalize may repeat this on the owner's PC **only** against such a dummy service, with his OK for
  that action (rule 5). Never against his real services.

## 7. Guards (pure, in plan.cpp, each with a selftest case)
- Boot-start (0) drivers: never planned by a preset. A single manual change is also refused in v1.
- System-start (1) drivers: only if the KB says `sysok`. The check uses the **live** start type, not the KB.
- No KB entry for this build: never in a preset (third-party and unknown items).
- `never` KB entries: never in a preset.
- Dependencies: disabling X while an item that isn't disabled lists X in `deps` produces a warning row in the
  plan ("<dependent> depends on it") and the row is unticked by default.
- TI-needed rows are excluded while the switch is off, with the reason shown.
- Each plan row has an include toggle (Space or click), so overrides need no custom-preset format.
